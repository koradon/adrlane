# Per-directory INDEX.md, hand-maintained, no YAML frontmatter

## Status

accepted

## Context and Problem Statement

Issue #33 asks for an `INDEX.md` per directory so LLM agents can scan a project's
documentation faster, especially in large, long-lived repositories. Today `docs/README.md`
is the only index — a single Path/Purpose table — and `docs/adr/`, `docs/specs/`,
`docs/ideas/`, and `docs/plans/` are flat folders navigated only by filename sorting (the
`YYYYMMDD-` prefix and sequential ADR numbering from ADR-0004). Every `adrlane-write-*`
skill also carries an explicit, repeated line: "Use `## Status` and `## Related` sections —
no YAML frontmatter." Any change here has to reconcile with that existing convention and
with ADR-0004, which already rejected a similar-shaped idea (dedicated `completed/`/
`waiting/` folders) specifically because a second location that must stay in sync with a
document's real state can drift from it.

## Considered Options

- **Scope**: `INDEX.md` per subdirectory under `docs/**` (adr, specs, ideas, plans, roadmap)
  versus a repo-wide mechanism covering arbitrary project directories.
- **Maintenance**: hand-maintained by each `adrlane-write-*` skill (appended when it creates
  or updates a file) versus generated by a new CLI command that derives entries from each
  file's `# ` title and `## Status` section.
- **Frontmatter**: keep the existing "no YAML frontmatter" rule versus introducing YAML
  frontmatter (title/status/created/related) as in the personal vault this project was
  partly inspired by.

## Decision Outcome

Chosen: `INDEX.md` scoped to `docs/**` only, hand-maintained by the `adrlane-write-*`
skills, with no YAML frontmatter.

- **Scope — `docs/**` only.** The issue's literal "each directory" is read as "each
  documentation directory adrlane manages," not the whole repository tree. This keeps the
  feature inside the doc types adrlane already owns and mirrors the existing per-type skill
  boundaries; a repo-wide directory-indexing feature would be a materially different,
  unscoped tool.
- **Hand-maintained, not generated.** A generated index (via a new CLI command) would avoid
  drift entirely, and was the initial recommendation, but it requires new CLI surface before
  any value is delivered. Hand-maintenance was chosen instead because each
  `adrlane-write-*` skill already edits a file in the target directory as part of its normal
  job — adding "update this directory's `INDEX.md`" is one more step in a flow that already
  exists, not a new process to remember. This knowingly reintroduces the same "second
  source of truth that can drift" risk ADR-0004 rejected for status folders; it is accepted
  here because the entry is a one-line title+link/status summary, not lifecycle state, and
  the cost of staleness (an outdated one-line summary) is much lower than the cost that
  motivated ADR-0004's rejection (files silently violating their own recorded status).
- **No YAML frontmatter.** Frontmatter would add little for the actual goal (faster LLM
  scans): `## Status` and `## Related` are already template-enforced across every doc type,
  so they are exactly as fast for an agent to read as an equivalent frontmatter field would
  be — the index file, not per-file metadata, is what removes the need to open N files. The
  one genuine advantage frontmatter has — a structured `related: []` YAML list instead of
  free-form prose links in `## Related`, useful for a reliable link graph — solves a
  different problem than directory scanning and is left for a future ADR if it's ever
  pursued on its own merits.

### Consequences

- Good, because directories that accumulate many docs (adr/specs/ideas/plans/roadmap) get a
  fast, single-file overview without opening every file — the concrete goal of issue #33.
- Good, because implementation stays inside the existing `adrlane-write-*` skill flow — no
  new CLI command, no new install-time behavior.
- Good, because the existing doc convention (`## Status`/`## Related`, no frontmatter) is
  preserved unchanged; no migration of existing docs is required.
- Bad, because a hand-maintained `INDEX.md` can drift from the directory's actual contents
  if a skill run is interrupted before updating it, or if a file is edited outside the
  skill flow (e.g., a manual edit or an external PR) — there is no automated check that
  catches this today.
- Bad, because `docs/README.md` and the new per-directory `INDEX.md` files are two indexes
  with overlapping purpose (repo-level map vs. directory-level map); this is intentional but
  worth naming so a future contributor doesn't try to collapse them.
